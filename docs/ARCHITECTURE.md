# Architektura — HarnasHub

## Przegląd

Monorepo: backend .NET oddzielony od frontendu React, komunikacja przez REST API + SignalR (live update dashboardu i dostępności).

Poza realną funkcją (narzędzie dla drużyny CS2) projekt służy też jako poligon do ćwiczenia programowania z asystą AI — cały kod powstaje i jest rozwijany w [Claude Code](https://claude.com/claude-code), więc konwencje w tym pliku (Vertical Slices, `ErrorOr`, wzorce inwersji zależności) są egzekwowane świadomie i konsekwentnie, nie tylko "bo tak wyszło".

```
HarnasHub/
├── backend/                    # ASP.NET Core Web API (.NET 10)
│   ├── src/
│   │   ├── HarnasHub.Core/            # encje, enumy, opcje konfiguracji — bez zewnętrznych zależności
│   │   ├── HarnasHub.Application/     # logika biznesowa jako Vertical Slices (Features/{Domain}/{Action}/), CQRS przez MediatR
│   │   ├── HarnasHub.Infrastructure/  # EF Core, PostgreSQL, powiadomienia (Discord, SignalR), EventReminderService
│   │   └── HarnasHub.Api/             # Minimal API endpoints, auth (JWT), SignalR Hub, DI, konfiguracja, serwowanie wwwroot/
│   └── tests/
│       └── HarnasHub.Tests/          # mirror struktury src/
├── frontend/                   # React 19 + TypeScript + Vite
│   ├── src/
│   │   ├── features/            # dashboard, calendar, availability, tasks, results, nades, map-strategy, tactics, stats, opponents...
│   │   ├── components/          # współdzielone komponenty UI (layout, common)
│   │   └── app/                 # routing, layout, providery, RealtimeSync (SignalR)
├── docs/
│   ├── ARCHITECTURE.md          # ten plik
│   ├── ROADMAP.md               # plan wdrażania
│   └── DEPLOYMENT.md            # jak i gdzie wdrożyć, jak przetestować po wdrożeniu
├── Dockerfile                   # multi-stage build: frontend (Node) + backend (.NET) → jeden obraz
├── docker-compose.yml           # postgres + lokalne S3 (SeaweedFS, :9000) do lokalnego dev
└── .github/workflows/           # CI: build + testy
```

Warstwy zależą do wewnątrz: `Api`/`Infrastructure` → `Application` → `Core`. `Core` nigdy nie referencuje wyższych warstw; jeśli niższa warstwa potrzebuje czegoś z wyższej, definiuje interfejs u siebie, a implementacja żyje wyżej (inversion of control).

## Backend — .NET 10 / ASP.NET Core

- **Vertical Slices** zamiast klasycznych warstw Service/Repository — każdy use case (`Features/Calendar/CreateEvent/`, `Features/Tasks/AssignTask/`) ma własny `Command`/`Query`, `Validator` (FluentValidation), `Handler` (MediatR, przypięty na `12.5.0` — wersje 13+ wymagają płatnej licencji, patrz [backend/CLAUDE.md](../backend/CLAUDE.md)).
- **Wynik operacji**: `ErrorOr<T>` jako typ zwracany z handlerów zamiast rzucania wyjątków dla oczekiwanych błędów biznesowych (np. "termin już zajęty", "nie możesz zmienić własnej roli").
- **EF Core + PostgreSQL** — encje (`HarnasHub.Core/Entities`):
  - `User` (`DiscordId`, `AvatarUrl`, `AccessLevel`: Guest / Player / Manager — zmieniany tylko przez Managera, nie na sobie samym) — bez hasła, tożsamość wyłącznie z Discorda. `AccessLevel` leci do bazy jako string (`HasConversion<string>`), więc dorzucenie nowej wartości enuma nie wymaga migracji. `User.IsCoach` (bool, osobne pole) to **niezależna** od `AccessLevel` flaga "jest Trenerem drużyny" — Zawodnik lub Zarządca może być Trenerem naraz, bo to dwa oddzielne pola, nie warianty jednego enuma. W JWT `AccessLevel` idzie jako pierwszy `ClaimTypes.Role`, a `IsCoach=true` dokłada **drugi** `ClaimTypes.Role="Coach"` claim — `RequireRole("Coach","Manager")` dopasowuje którykolwiek, więc istniejące polityki autoryzacji nie wymagały zmian; `ICurrentUserService.Role` nadal zwraca sam `AccessLevel` (pierwszy claim), a nowy `ICurrentUserService.IsCoach` czyta obecność claimu "Coach"
  - `User.TeamRole` (IGL / EntryFragger / Support / AWPer / Lurker / Rifler / Bambik, nullable) — **główna** rola w grze, osobna od `Role` (poziom uprawnień); ustawia ją Coach lub Manager (`PATCH /api/roster/{userId}/team-role`). Dodatkowe/zapasowe role (np. "drugi AWPer") żyją osobno w `UserSecondaryTeamRole` (many-to-many po `(UserId, TeamRole)`, unikalny indeks) i mają własny slice `Features/Roster/SetSecondaryTeamRoles` (bulk-replace całego zbioru na raz, odrzuca rolę pokrywającą się z `TeamRole`)
  - `User.RosterSlot` (Main / Bench / StandIn, nullable, string w bazie) — miejsce w składzie; Main ograniczone do 5 osób (walidacja w `UpdateRosterSlotHandler`, licząca aktualnych Main przy każdej zmianie). StandIn nigdy nie pojawia się w siatce dostępności (`GetWeekAvailabilityHandler` filtruje) — tak samo Gość (`AccessLevel.Guest`) i każdy bez slotu, chyba że ma `IsCoach`; sortowanie: Trener zawsze na końcu (niezależnie od slotu), dalej Main przed Bench, alfabetycznie po nazwie
  - `User.PinColor` (Orange / Yellow / Purple / Green / Blue, nullable) — własny kolor pinezki na radarze pozycji; ustawialny wyłącznie przez zawodnika **głównego składu** (`PATCH /api/roster/me/pin-color`, handler odrzuca próbę dla `RosterSlot != Main`); bez ustawionego koloru pin wraca do automatycznego (hash z `UserId`)
  - `User.InGameNickname` (nullable, 2–32 znaki) — własny nick gracza, edytowany (i **czyszczony** przez pusty string → `null`) wyłącznie przez samego zainteresowanego (`PATCH /api/roster/me/nickname`, bez parametru `userId` w ścieżce, żeby nie dało się podmienić celu; sekcja `/settings` z kołem zębatym w pasku). Nie ma go w JWT, więc frontend dociąga go z listy składu i trzyma w `useAuthStore`; w UI nick ma pierwszeństwo przed `DisplayName` z Discorda — konsekwentnie, łącznie z siatką dostępności i pinami na radarze
  - `User.SteamId64` (nullable **`string`**, nie `long` — jak `DiscordId`, bo SteamID64 przekracza `Number.MAX_SAFE_INTEGER` i jako liczba w JSON tracił(by) precyzję w przeglądarce) — ustawiany wyłącznie przez samego zainteresowanego (`PATCH /api/roster/me/steam-id`, ten sam wzorzec co `InGameNickname`), waliduje dokładnie 17 cyfr ≥ najniższego wydanego SteamID64. Czytają go dwa miejsca, oba przy parsowaniu demki: dopasowanie graczy przy imporcie staty (`Features/Stats/ImportStatsFromDemo`) i rozpoznanie, po której stronie w danej rundzie stała nasza drużyna, przy wyliczaniu wyniku meczu (`Features/Results/Shared/DemoScoreCalculator`)
  - `User.ShowInStats` / `User.ShowInCalendar` (bool, domyślnie `true`, także domyślna wartość w bazie) — przełączniki widoczności ustawiane wyłącznie przez Managera (`PATCH /api/roster/{userId}/visibility` `{showInStats, showInCalendar}`, `Features/Roster/SetVisibility`; powiadamia tematy `roster`, `availability-week`, `dashboard`, `stats`). Ukrycie **nigdy nie usuwa danych** i można je cofnąć w każdej chwili. `ShowInStats=false` wyłącza gracza z rankingu (`GetPlayerLeaderboardHandler`) i ze strony „My” raportu rywala (`OurRosterFaceit`: rozpoznawanie graczy FACEIT, synchronizacja, forma indywidualna) — jego własne „Moje statystyki” zostają. Trend drużyny (`GetTeamTrend`) jest zespołowy, nie per gracz, więc nie jest filtrowany. `ShowInCalendar=false` wyłącza gracza z siatki dostępności (`GetWeekAvailabilityHandler`), list dnia na dashboardzie, podsumowania frekwencji (`Attendance/GetSummary`) i zliczania incydentów na dashboardzie; ukryty gracz dostaje w odpowiedzi tygodnia **tylko własny wiersz** z `hiddenFromCalendar=true` (żeby dalej mógł edytować swoją dostępność), a frontend (`computeDaySummary`, lista nieobecnych) pomija takie wiersze w licznikach „X/Y dostępnych”. Lista dostępności wydarzenia (`GetEventAvailability`) nie jest filtrowana.
  - `User.FaceitNickname` (nullable, max 64) — ręczny nick FACEIT dla graczy bez SteamID albo z SteamID niepowiązanym z kontem FACEIT; ustawia go Manager (`PATCH /api/roster/{userId}/faceit-nickname` `{nickname}`, `null` czyści, pusty/zbyt długi odrzuca walidator). `OurRosterFaceit.ResolveAsync` (wołany przez `FaceitSync.ResolveOurPlayersAsync`) rozpoznaje każdego gracza widocznego w statystykach najpierw po SteamID64, potem po nicku (`IFaceitClient.GetPlayerByNicknameAsync`, `GET /players?nickname=`), z użyciem cache `FaceitPlayers` (`ProfileMaxAge`). Raport rywala dostaje na żywo (w `WithLiveFieldsAsync`, nie w snapshocie) opcjonalne pole `UnresolvedOurPlayers` — gracze składu (Main/Bench) bez konta FACEIT z powodem: „brak SteamID i nicku FACEIT”, „SteamID bez konta FACEIT — ustaw nick FACEIT w panelu admina” albo „nie znaleziono nicku FACEIT”; UI pokazuje je na zakładce „My” (Manager dostaje link do `/admin`). Migracja: trzy nowe kolumny w `Users`.
  - `Event` (Match / Tournament / Training / PickupGame / Scrim) → `Availability` (per user, per event, unikalny indeks na parze). Opcjonalne `Event.Opponent` (wolny tekst, max 100) — formularz pokazuje je tylko dla Match/Tournament/Scrim.
  - **Przeciwnik nie jest osobną encją.** Nazwa żyje jako wolny tekst w trzech miejscach (`OpponentNote.OpponentName`, `MatchResult.Opponent`, `Event.Opponent`), a profil (`Features/OpponentNotes/{GetOpponents,GetOpponentProfile}`) skleja je po kluczu `OpponentNames.ToKey` (trim + lower-case, w EF `x.Trim().ToLower() == key`). Wielkość liter i spacje nie rozbijają przeciwnika na dwóch; literówki już tak — dlatego każde pole nazwy w UI (`OpponentNameInput`) podpowiada znane nazwy przez `<datalist>`. Nazwa wyświetlana = ostatnio użyta pisownia.
  - **Zarządzanie przeciwnikami** (`Features/OpponentManagement/{DeleteOpponent,GetOpponentDeletePreview,HideOpponent,UnhideOpponent,RenameOpponent}`, endpointy `/api/opponents` tylko Coach/Manager). Ponieważ przeciwnik to tylko klucz nazwy, sprzątanie literówek i testowych wpisów ma trzy narzędzia. **Usuń** (`DELETE /api/opponents?name=&includeHistory=`) kasuje dane „tylko scoutingowe”: notatki, `OpponentFaceitLink`, `OpponentReportSnapshot`, `OpponentDemoAnalysis` wraz z osiami czasu w S3 (`opponents/{slug}/…`, błąd usunięcia obiektu jest logowany i nie przerywa operacji). Wyniki i wydarzenia z tą nazwą nie znikają po cichu: `GET /api/opponents/delete-preview?name=` zwraca liczby dla dialogu, a dopiero `includeHistory=true` usuwa je istniejącymi komendami `DeleteResultCommand`/`DeleteEventCommand` (statystyki, osie czasu meczów, powiadomienia działają jak zwykle). Bez tej flagi mecze zostają w historii wyników, a przeciwnik znika z listy (pod spodem jest ukrywany, bo lista powstaje z nazw w wynikach). Ponowne użycie nazwy — nowa notatka, powiązanie FACEIT, wydarzenie albo wynik, lub edycja zmieniająca nazwę na tę przeciwnika — przywraca go automatycznie (`OpponentNotes/Shared/OpponentRevival`), z czystymi danymi scoutingowymi; sama edycja starego meczu bez zmiany nazwy go nie przywraca. **Ukryj/Przywróć** (`POST /hide`, `/unhide`) to encja `HiddenOpponent` (`OpponentKey` unikalny, `DisplayName`, `HiddenAtUtc`, `HiddenByUserId`): `GetOpponents` pomija ukrytych (stąd znikają też z podpowiedzi `OpponentNameInput`), `?includeHidden=true` zwraca ich z `IsHidden` (UI: „Pokaż ukrytych”), historia zostaje nietknięta. **Zmień nazwę / scal** (`POST /rename {from, to}`) w jednej transakcji (jeden `SaveChanges`) przepisuje nazwę w notatkach, wynikach i wydarzeniach, przenosi demki, flagę ukrycia oraz link FACEIT i snapshot raportu na klucz docelowy; gdy cel ma już własny link/snapshot, zostaje docelowy, a źródłowy jest porzucany (`FaceitDataKept` w odpowiedzi). Zmiana samej wielkości liter (ten sam klucz) aktualizuje tylko pisownię. Frontend: menu „⋯” (`OpponentActionsMenu`) na karcie listy i profilu, `DeleteOpponentDialog` pokazuje liczby („3 wyniki, 1 wydarzenie”) i jawny checkbox „Usuń też wyniki i wydarzenia”; mutacje unieważniają `opponents`, `results`, `calendar`, `dashboard`, `stats`, `veto`.
  - **Dodawanie przeciwnika od razu z FACEIT/demką**: lista `GetOpponents` (i nazwa w profilu) obejmuje też przeciwników istniejących tylko przez `OpponentFaceitLink` (nazwa = `DisplayName`) albo `OpponentDemoAnalysis` (nazwa = z linku, z ukrycia, a w ostateczności sam klucz); ukryci nadal są pomijani (`includeHidden` je pokazuje). `AnalyzeOpponentDemo` — tak jak powiązanie FACEIT — woła `OpponentRevival`, więc użycie nazwy ukrytego przeciwnika przywraca go. Frontend: przycisk „+ Dodaj przeciwnika” na `/opponents` otwiera `AddOpponentForm` (nazwa z podpowiedziami i ostrzeżeniem „już istnieje” + link do raportu, opcjonalne pole FACEIT, opcjonalne pliki `.dem`; modal chroniony `useModalGuard`). „Dodaj” startuje te same zadania co raport (`PUT /api/opponents/report/link` oraz presigned upload + analiza per demka z oryginalną nazwą pliku), po czym przechodzi do `/opponents/report?name=…`, gdzie postęp zadania powiązania trwa dalej (slot `faceit-link:{klucz}`). Wymagane jest co najmniej FACEIT lub demka — przeciwnik bez żadnych danych nie ma gdzie istnieć (nie ma encji przeciwnika), więc samą nazwę dodaje się przez „+ Dodaj notatkę” na profilu.
  - `PlayerAvailabilityDay` — dostępność dzienna niezależna od wydarzeń (Available / PartiallyAvailable z zakresem godzin / Off), unikalny indeks `(UserId, Date)`. Edycja dnia z przeszłości zablokowana w handlerze (`SetDayAvailabilityHandler`, wyjątek dla Coach/Manager); frontend rozdziela widok na zakładki „Nadchodzące" (dziś + przyszłość, edytowalne) i „Historia" (tylko odczyt, osobna nawigacja tygodniami). Zmiana statusu i notatki zapisuje się od razu po kliknięciu (bez osobnego „Zapisz" poza notatką) — patrz `DayAvailabilityEditor`
  - `Vacation` — zakres dni wolnych gracza; w widoku tygodniowym nadpisuje dostępność dzienną na `Off` z flagą `IsVacation`. Pełne CRUD (`Features/Availability/{SetVacation,UpdateVacation,DeleteVacation}`) — edycja w miejscu zamiast usuń-i-dodaj-od-nowa, ta sama reguła autoryzacji co przy usuwaniu (właściciel lub Coach/Manager)
  - Logikę "efektywnego statusu dnia" (urlop > deklaracja > `NotSet`) trzyma jedna klasa `Features/Availability/Shared/EffectiveAvailabilityCalculator` — używa jej zarówno widok tygodniowy, jak i dashboard (dziś/jutro), żeby nie rozjechały się interpretacje urlopu
  - `TaskItem` → przypisany do `User`, status Todo/PendingReview/Done/NeedsRework (pełen cykl: zawodnik zgłasza `Todo`/`NeedsRework` → `PendingReview` przez `Features/Tasks/SubmitTaskForReview`, Coach/Manager zatwierdza do `Done` (`ApproveTask`) albo cofa do `NeedsRework` (`RejectTask`); `Features/Tasks/GetAllTasks` daje Coach/Managerowi podgląd zadań wszystkich zawodników z `DeleteTask` do kasowania pomyłek). Opcjonalny `DueAtUtc` i opcjonalny `TrainingMaterialId` (luźny link bez FK, jak `TacticPoint.NadeEntryId`) pozwalają Coach/Managerowi doczepić do zadania konkretny materiał z biblioteki do obejrzenia — `GetMyTasksHandler`/`GetAllTasksHandler` dołączają tytuł/URL materiału jednym `GroupJoin`, więc zawodnik widzi link bezpośrednio na liście swoich zadań, bez osobnego zapytania
  - `MatchResult` — wynik + opcjonalny link do demki (`DemoUrl`, zwykły string, nie plik). `OurScore`/`OpponentScore`/`MapName` na encji zostają nienullowalne, ale w `AddResultCommand` są opcjonalne: przy dodawaniu wyniku można dołączyć plik `.dem`, z którego handler wylicza wynik i mapę (patrz „Wynik i mapa z demki" niżej), a wpisane ręcznie wartości są wtedy tylko fallbackiem. `Category` (`MatchCategory`: Scrimmage/League/Tournament, string w bazie) rozróżnia typ rozgrywki; `TournamentId`/`LeagueId` to luźne linki (bez FK, jak `TacticPoint.NadeEntryId`) do `Tournament`/`League`, ustawione tylko gdy `Category` na to wskazuje (pilnuje `AddResultCommandValidator`, oba pola po obu stronach warunkowo — z jawnym `ApplyConditionTo.CurrentValidator`, bo domyślnie `.When()` w FluentValidation działa wstecz na cały łańcuch reguł danego `RuleFor`, nie tylko na poprzedzający walidator)
  - `Tournament` — `Id`/`Name`/`CreatedByUserId`/`CreatedAtUtc`, realna encja zamiast wolnego tekstu w `MatchResult`, żeby literówka w nazwie nie rozbijała grupowania wyników na `/results`
  - `League` — `Id`/`Name`/`Season` (wolny tekst, np. "2026 Wiosna")/`Type` (`LeagueType`: Online/Lan/Division1/Division2/Other, string w bazie)/`CreatedByUserId`/`CreatedAtUtc`
  - `NadeEntry` — per mapa (`MapName` jako enum: Dust2 / Mirage / Inferno / Nuke / Ancient / Anubis / Cache — aktualna pula 2026, w bazie trzymany jako string przez `HasConversion<string>`), typ granatu, link YouTube. Rotacja puli map = nowa wartość enuma + migracja normalizująca stare wpisy (wzór: `ConvertNadeMapNameToEnum`). Opcjonalna pozycja lądowania na radarze (`LandingX`/`LandingY`, ułamki [0,1] jak w `MapPositionAssignment`, nullable — stare wpisy bez pinezki nadal działają, pokazują się tylko na liście) ustawiana osobnym slice'em `Features/Nades/UpdateNadePosition` (autor wpisu lub Coach/Manager, jak przy usuwaniu), żeby nie psuć kontraktu `AddNade`
  - `MapPositionAssignment` — pozycja startowa jednego gracza na danej mapie i stronie (`MapSide`: CT / T, w bazie jako string). `X`/`Y` to **ułamki [0,1] względem radaru**, nie piksele — dzięki temu pinezki są niezależne od rozmiaru obrazu i skalują się z kontenerem. Unikalny indeks `(MapName, Side, UserId)` = jeden gracz ma jedno miejsce na mapie/stronie, a slice `Features/MapStrategy/SetPlayerPosition` robi po tym kluczu upsert (wzór jak `SetAvailability`)
  - `MapTextAnnotation` — dowolna notatka tekstowa na radarze (np. opis miejscówki), **nieprzypisana do gracza** — w przeciwieństwie do `MapPositionAssignment` może ich być wiele na tej samej mapie/stronie, więc brak unikalnego indeksu, tożsamość to zwykłe `Id`. `X`/`Y` — te same ułamki [0,1] co w `MapPositionAssignment`. `Color` (hex string) i `FontSizePx` (10-40) są edytowalne z poziomu frontu razem z treścią, przez jeden slice `Features/MapStrategy/UpdateTextAnnotation` (przeciąganie pinezki i edycja stylu/treści to ta sama komenda, tylko inne pola się zmieniają). CRUD: `AddTextAnnotation`/`UpdateTextAnnotation`/`RemoveTextAnnotation`/`GetMapTextAnnotations`, wszystkie poza odczytem ograniczone do Coach/Manager. Radar na froncie (`MapRadar.tsx`) obsługuje też scroll-zoom + pan (`useMapZoom` — transform `scale`/`translate` na wewnętrznym kontenerze, licznik pozycji pinezek liczony z jego `getBoundingClientRect()`, więc działa niezależnie od aktualnego przybliżenia)
  - `Tactic` → `TacticPoint` (1-do-wielu, kaskadowe usuwanie) — zapisana taktyka drużyny per mapa i strona (`MapSide`), z tagiem ekonomii (`EconomyType`: Eco/ForceBuy/FullBuy/AntiEco) i dowolną liczbą ponumerowanych punktów na radarze (`X`/`Y` — te same ułamki [0,1] co w `MapPositionAssignment`), z których każdy ma opcjonalny opis i opcjonalny luźny link do `NadeEntry.Id` (bez FK, jak `CreatedByUserId` gdzie indziej). W przeciwieństwie do `MapPositionAssignment` (jedna pozycja na gracza) punkty taktyki nie są przypisane do konkretnego gracza — to plan, nie obsada. Tworzy/edytuje/usuwa wyłącznie Coach/Manager (`Features/Tactics/UpdateTactic` zapisuje metadane **i** cały układ punktów jedną komendą — edytor wysyła kompletną listę na każdy "Zapisz", stare wiersze kasowane jawnie przez `DbSet.RemoveRange` zamiast liczyć na wykrywanie zmian w kolekcji nawigacyjnej, bo EF Core oznacza nowo dodane encje z jawnie ustawionym kluczem jako `Modified`, nie `Added`, gdy trafiają do śledzonego kontekstu przez samą nawigację). Odczyt (lista + szczegóły) dla całej drużyny.
  - `TrainingMaterial` — link + kategoria (`MaterialCategory`: Grenades/Tactics/Aim/Positioning/VodReview/Communication/Other, string w bazie przez `HasConversion<string>`, opcjonalna — lista rozwijana na froncie zamiast dawnego wolnego tekstu)
  - `MapPoolEntry` — status mapy w puli drużyny (`MapPoolStatus`: Core/Playable/Learning/Ban, string w bazie) + krótka uwaga; unikalny indeks na `MapName`, brak wiersza = mapa nieustalona. `Features/MapPool/GetMapPool` zawsze zwraca **wszystkie** mapy z enuma `MapName`, a bilans liczy z `MatchResult.MapName` (wolny tekst, dopasowywany do enuma `Enum.TryParse(ignoreCase)` po `Trim`; mapy spoza puli, np. Overpass, są pomijane). Opcjonalny filtr `MatchCategory`.
  - `TeamInfoEntry` (`Category` ≤ 50, `Title` ≤ 100, `Value` ≤ 2000 — zwykły tekst: link, `IP:port`, komenda `connect`, fragment konfiguracji; `IsSecret`, `SortOrder`, `UpdatedAtUtc`, `UpdatedByUserId`) — stałe informacje techniczne drużyny (strona „Info”). Slice’y `Features/TeamInfo/{GetTeamInfo,CreateTeamInfoEntry,UpdateTeamInfoEntry,DeleteTeamInfoEntry,ReorderTeamInfoEntries}`; endpointy `/api/team-info` (GET dla każdego członka drużyny, bez Guestów; POST, PUT `/{id}`, DELETE `/{id}`, PUT `/order` `{orderedIds}` tylko Coach/Manager; temat SignalR `team-info`). Wartości „sekretne” serwer zwraca członkom drużyny normalnie — maskowanie (`••••••` + „Pokaż”) dotyczy wyłącznie UI. Nowy wpis i zmiana kategorii dopisują wpis na koniec kategorii; `order` zapisuje kolejność jednej kategorii i odrzuca nieznane identyfikatory w całości.

- **Forma indywidualna w raporcie rywala** (`IndividualGameLines`, `PlayerFormCalculator`, `MapComfortCalculator`, `IndividualSignal`, `IndividualInsightRules`, pole `OpponentReportDto.IndividualForm`, opcjonalne — stare snapshoty czytają się jako `null`):
  - *Drużynowy vs solo*: mecz (mapa) jest drużynowy dla składu, gdy ≥ 3 powiązanych graczy stoi po jednej stronie (`TeamMatchDetector.FindSide`; u rywala: mecz oficjalny jego drużyny FACEIT albo ≥ 3 graczy ze składu — patrz „Mecze oficjalne i sezon ESEA”); każdy inny wiersz statystyk gracza z okna 120 dni (także mecz przeciwko koledze ze składu) to mecz solo. Wygrana = wygrała frakcja gracza.
  - *Per gracz* (rywal z `OpponentFaceitLink`, my z graczy rozwiązanych po SteamID64): ELO/poziom z `FaceitPlayer`, mecze, WR, K/D, ADR, HS%, per mapa z puli — udział w jego meczach i podział drużynowe/solo; strzałka formy = K/D z ostatnich 10 meczów vs wcześniejsze (min. 5), próg ±0,15.
  - *Komfort mapy* (tylko mecze solo, by nie liczyć dwa razy tego, co już jest w metrykach drużynowych): oceniany jest gracz z ≥ 10 meczami solo; „regularnie” = ≥ 3 mecze solo na mapie, „unika” = 0–1. Mapa „unikana”, gdy unika jej większość ocenionych (≥ 2) i najwyżej 1 gra regularnie; „komfortowa”, gdy większość gra regularnie, a ich średni WR ≥ 50%.
  - *Blending z przewidywanym veto rywala*: sygnał solo działa tylko przy ≥ 3 ocenionych graczach i ma wagę `w = k / (k + n)`, `k = 5`, `n = max(mecze drużynowe na mapie, wszystkie mecze drużynowe / liczba map w puli)` (nie granie mapy w wielu meczach drużynowych też jest dowodem). Preferencja do symulacji veto: `(1 − w)·(udział + wygładzony WR) + w·(średni udział solo + wygładzony WR solo regularnych)`, przy czym preferencja solo = 0, gdy nikt jej regularnie nie gra. Przy ≥ 5 meczach drużynowych reguły ban/pick są jak dawniej (z progami próby i lifetime z punktu „Model decyzji veto”), plus: mapa z ≤ 2 meczami drużynowymi i „unikana” solo → ban. Przy < 5 meczach drużynowych: „unikana” → możliwy ban, 2 najbardziej komfortowe → możliwy pick, reszta „?”.
  - *Nasza strona (przewaga)*: forma solo przesuwa tylko prior wygładzania — `(wygrane + k·prior) / (mecze + k)`, prior = średni wygładzony WR solo regularnych (≥ 2) obcięty do 0,4–0,6 (bez danych 0,5), osobno dla nas i dla nich. Wpływ to `k/(k+mecze)·|prior − 0,5|`: maks. 10 pp bez meczów, 5 pp przy 5 meczach, ~1,4 pp przy 30.
  - *TL;DR*: nowe reguły (unikana mapa solo → prawie pewny ban, gracz w formie / bez formy, komfortowa mapa rywala → możliwy pick, nasza mocna mapa solo); wszystko sortowane po ważności i obcięte do 5 punktów, a mapa z reguły solo nie jest powtarzana w „Nie grają …”.
- **Model decyzji veto i aktywny skład rywala** (`VetoMapScorer`, `SampleThresholds`, `RecencyWeight`, `ActiveLineupResolver`, `LifetimeMapCalculator`, `FaceitLifetimeStats`, `FaceitHistoryPager`):
  - *Znajomość mapy (`VetoFamiliarity`)* — mapy, których nie gramy, banujemy przed mapami, które znamy, niezależnie od bilansu na znanej mapie. Mapa jest „znana”, gdy ma status Core/„gramy” w puli, albo (bez statusu) ≥ 3 mecze drużynowe (wyniki HarnasHub + mecze drużynowe FACEIT) lub większość składu gra ją regularnie solo (≥ 3 regularnych graczy, albo 2 + duże doświadczenie lifetime; sam lifetime nie wystarcza; `MapComparisonDto.OurPlaysIndividually` w snapshocie). Gdy trener oznaczył w puli choć jedną mapę jako Core/„gramy”, pula jest źródłem prawdy: mapa bez statusu jest znana tylko z meczów drużynowych, sama gra solo już nie wystarcza (`VetoFamiliarity.ApplyCoachPool`). To poziom (`VetoBanTier`), nie punkty: stały ban › mapy, których nie gramy, oraz mapy „w przygotowaniu” › znane mapy z realnym ujemnym dowodem › pozostałe znane. Znana mapa trafia do banów dopiero, gdy zabraknie map, których nie gramy (albo gdy pula oznacza ją jako ban/„w przygotowaniu”); bilans porządkuje tylko znane mapy między sobą (nadal od 5 meczów). Nasza komfortowa mapa (Core albo ≥ 3 mecze i więcej wygranych niż porażek) nigdy nie jest banowana tylko dlatego, że rywal jest na niej mocny lub ją wybierał. Pick wymaga znanej mapy. Gdy żadna mapa nie jest znana (brak danych), poziom znajomości jest wyłączony. Powody/notatki: „nie gramy tej mapy (1 mecz) — ban w pierwszej kolejności”, „znamy mapę (6 meczów), mimo słabego bilansu 17% — nie banujemy, dopóki są mapy, których nie gramy” (gdy mimo to trafia do banów: „…ale bilans 17% — ban dopiero po mapach, których nie gramy”), „ich mocna mapa, ale i nasza (3-1, 4 mecze) — nie banujemy”. Ten sam porządek stosują kolumna „My” macierzy, symulacja BO1/BO3 (`VetoCandidate.OurTier`; ban znanej mapy po odpadnięciu niegranych: „Mapy, których nie gramy, już odpadły — …”) i wniosek „Uwaga na …” („kandydat do bana” tylko, gdy nasze veto ją banuje).
  - *Nasze picki/bany* — kolejność zaufania: status w puli map ustawiony przez trenera (stały ban → zawsze ban, −100; komfortowa/Core +40; „gramy” +10; w przygotowaniu −25; brak statusu 0) › znajomość mapy (wyżej) › nasz bilans (wyniki HarnasHub + mecze drużynowe FACEIT) i skuteczność rywala na mapie › bilans z rywalem, jego zapisane picki/bany, taktyki › forma solo naszych graczy (prior 0,4–0,6 → maks. ±5 pkt). Bilans liczy się dopiero od `SampleThresholds.MinGamesForWinRate = 5` meczów na mapie (wygładzony WR, `k = 5`, ×60, maks. ±25); poniżej tylko powód „Nasz bilans 0-2 — za mało danych (2 mecze), nie wpływa na rekomendację”. Skuteczność rywala (jego WR ważony świeżością, wygładzony, od 5 meczów, ×60, maks. ±15) daje powód „Przewaga rywala: ich 70% wygranych przy 9 meczach”. Dodatkowe bany (ponad stałe) dostają najpierw mapy, których nie gramy, a potem tylko znane mapy, których suma punktów bez składnika solo jest ujemna — mała próbka ani sama forma solo nigdy nie wymuszą bana znanej mapy. `Note` (np. „w puli: gramy, za mało danych (my: 2 mecze)”) trafia do kroków symulowanego veto. Snapshot zasila `GET /api/veto/suggestion` przez `OpponentReportSnapshots.ApplyFaceit` (stare snapshoty bez `OurFaceitWins` liczą tylko bilans wewnętrzny).
  - *Strona rywala*: „Nie grają X → prawie pewny ban” wymaga `SampleThresholds.MinTeamGamesForAvoidance = 15` meczów drużynowych i nie może przeczyć danym indywidualnym — gdy aktywny skład gra mapę regularnie solo (≥ 2 regularnych) albo dużo lifetime, wynik to „Rzadko grają drużynowo (1 z 12), ale indywidualnie dużo (113 meczów lifetime składu) → niepewne” („?”). Przy 5–14 meczach rzadko grana mapa to „?” (chyba że unikana także solo → „możliwy ban”). Procent wygranych rywala na mapie jest cytowany (powody, TL;DR „Słabi na…”/„Uwaga na…”) dopiero od 5 meczów; nasz poniżej 5 meczów jako „za mało danych (n meczów)”.
  - *Ważenie świeżością*: waga meczu `0,5^(wiek / 45 dni)` (`RecencyWeight.HalfLifeDays`); używana w wygładzonym WR i udziale mapy rywala (`MapMetrics.SmoothedWinRate`, `DecisionShare` → preferencja i przewaga) oraz w udziale solo i wygładzonym WR solo komfortu. Liczby meczów i surowe WR na ekranie zostają nieważone; strzałka formy gracza już jest „ostatnie 10 vs wcześniejsze”.

Współrzędne świata są w każdej osi czasu (`DemoPlayerTrack.World`, `DemoPosition.World*`), więc stare osie czasu można przeliczyć bez ponownego parsowania demek.
- **Wdrożenie**: `Program.cs` na starcie sam aplikuje migracje (`Database.MigrateAsync()`) i serwuje `wwwroot/` jako SPA fallback — jeden kontener = cały produkt. Szczegóły i checklista testowa: [DEPLOYMENT.md](DEPLOYMENT.md).

Zamknięcie zajętego okna nie przerywa zadania w tle: analiza demki w `AddResultForm` ma `slot` w `useJobStore`, a wynik wraca do formularza po ponownym otwarciu. Prefill z analizy/FACEIT (`buildAnalysisPatch`) nigdy nie nadpisuje pól, które użytkownik już ruszył.
