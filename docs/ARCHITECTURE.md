# Architektura — HarnasHub

## Przegląd

Monorepo: backend .NET oddzielony od frontendu React, komunikacja przez REST API + SignalR (live update dashboardu i dostępności).

Poza realną funkcją (narzędzie dla drużyny CS2) projekt służy też jako poligon do ćwiczenia programowania z asystą AI — cały kod powstaje i jest rozwijany w [Claude Code](https://claude.com/claude-code), więc konwencje w tym pliku (Vertical Slices, `ErrorOr`, wzorce inwersji zależności) są egzekwowane świadomie i konsekwentnie, nie tylko "bo tak wyszło".

```
HarnasHub/
├── backend/                    # ASP.NET Core Web API (.NET 10)
│   ├── src/
│   │   ├── HarnasHub.Core/            # encje, enumy, opcje konfiguracji — bez zewnętrznych zależności
│   │   ├── HarnasHub.Application/     # logika biznesowa jako Vertical Slices (Features/{Domain}/{Action}/), CQRS przez MediatR
│   │   ├── HarnasHub.Infrastructure/  # EF Core, PostgreSQL, powiadomienia (Discord, SignalR), EventReminderService
│   │   └── HarnasHub.Api/             # Minimal API endpoints, auth (JWT), SignalR Hub, DI, konfiguracja, serwowanie wwwroot/
│   └── tests/
│       └── HarnasHub.Tests/          # mirror struktury src/
├── frontend/                   # React 19 + TypeScript + Vite
│   ├── src/
│   │   ├── features/            # dashboard, calendar, availability, tasks, results, nades, map-strategy, tactics, stats, opponents...
│   │   ├── components/          # współdzielone komponenty UI (layout, common)
│   │   └── app/                 # routing, layout, providery, RealtimeSync (SignalR)
├── docs/
│   ├── ARCHITECTURE.md          # ten plik
│   ├── ROADMAP.md               # plan wdrażania
│   └── DEPLOYMENT.md            # jak i gdzie wdrożyć, jak przetestować po wdrożeniu
├── Dockerfile                   # multi-stage build: frontend (Node) + backend (.NET) → jeden obraz
├── docker-compose.yml           # postgres + lokalne S3 (SeaweedFS, :9000) do lokalnego dev
└── .github/workflows/           # CI: build + testy
```

Warstwy zależą do wewnątrz: `Api`/`Infrastructure` → `Application` → `Core`. `Core` nigdy nie referencuje wyższych warstw; jeśli niższa warstwa potrzebuje czegoś z wyższej, definiuje interfejs u siebie, a implementacja żyje wyżej (inversion of control).

## Backend — .NET 10 / ASP.NET Core

- **Vertical Slices** zamiast klasycznych warstw Service/Repository — każdy use case (`Features/Calendar/CreateEvent/`, `Features/Tasks/AssignTask/`) ma własny `Command`/`Query`, `Validator` (FluentValidation), `Handler` (MediatR, przypięty na `12.5.0` — wersje 13+ wymagają płatnej licencji, patrz [backend/CLAUDE.md](../backend/CLAUDE.md)).
- **Wynik operacji**: `ErrorOr<T>` jako typ zwracany z handlerów zamiast rzucania wyjątków dla oczekiwanych błędów biznesowych (np. "termin już zajęty", "nie możesz zmienić własnej roli").
- **EF Core + PostgreSQL** — encje (`HarnasHub.Core/Entities`):
  - `User` (`DiscordId`, `AvatarUrl`, `AccessLevel`: Guest / Player / Manager — zmieniany tylko przez Managera, nie na sobie samym) — bez hasła, tożsamość wyłącznie z Discorda. `AccessLevel` leci do bazy jako string (`HasConversion<string>`), więc dorzucenie nowej wartości enuma nie wymaga migracji. `User.IsCoach` (bool, osobne pole) to **niezależna** od `AccessLevel` flaga "jest Trenerem drużyny" — Zawodnik lub Zarządca może być Trenerem naraz, bo to dwa oddzielne pola, nie warianty jednego enuma. W JWT `AccessLevel` idzie jako pierwszy `ClaimTypes.Role`, a `IsCoach=true` dokłada **drugi** `ClaimTypes.Role="Coach"` claim — `RequireRole("Coach","Manager")` dopasowuje którykolwiek, więc istniejące polityki autoryzacji nie wymagały zmian; `ICurrentUserService.Role` nadal zwraca sam `AccessLevel` (pierwszy claim), a nowy `ICurrentUserService.IsCoach` czyta obecność claimu "Coach"
  - `User.TeamRole` (IGL / EntryFragger / Support / AWPer / Lurker / Rifler / Bambik, nullable) — **główna** rola w grze, osobna od `Role` (poziom uprawnień); ustawia ją Coach lub Manager (`PATCH /api/roster/{userId}/team-role`). Dodatkowe/zapasowe role (np. "drugi AWPer") żyją osobno w `UserSecondaryTeamRole` (many-to-many po `(UserId, TeamRole)`, unikalny indeks) i mają własny slice `Features/Roster/SetSecondaryTeamRoles` (bulk-replace całego zbioru na raz, odrzuca rolę pokrywającą się z `TeamRole`)
  - `User.RosterSlot` (Main / Bench / StandIn, nullable, string w bazie) — miejsce w składzie; Main ograniczone do 5 osób (walidacja w `UpdateRosterSlotHandler`, licząca aktualnych Main przy każdej zmianie). StandIn nigdy nie pojawia się w siatce dostępności (`GetWeekAvailabilityHandler` filtruje) — tak samo Gość (`AccessLevel.Guest`) i każdy bez slotu, chyba że ma `IsCoach`; sortowanie: Trener zawsze na końcu (niezależnie od slotu), dalej Main przed Bench, alfabetycznie po nazwie
  - `User.PinColor` (Orange / Yellow / Purple / Green / Blue, nullable) — własny kolor pinezki na radarze pozycji; ustawialny wyłącznie przez zawodnika **głównego składu** (`PATCH /api/roster/me/pin-color`, handler odrzuca próbę dla `RosterSlot != Main`); bez ustawionego koloru pin wraca do automatycznego (hash z `UserId`)
  - `User.InGameNickname` (nullable, 2–32 znaki) — własny nick gracza, edytowany (i **czyszczony** przez pusty string → `null`) wyłącznie przez samego zainteresowanego (`PATCH /api/roster/me/nickname`, bez parametru `userId` w ścieżce, żeby nie dało się podmienić celu; sekcja `/settings` z kołem zębatym w pasku). Nie ma go w JWT, więc frontend dociąga go z listy składu i trzyma w `useAuthStore`; w UI nick ma pierwszeństwo przed `DisplayName` z Discorda — konsekwentnie, łącznie z siatką dostępności i pinami na radarze
  - `User.SteamId64` (nullable **`string`**, nie `long` — jak `DiscordId`, bo SteamID64 przekracza `Number.MAX_SAFE_INTEGER` i jako liczba w JSON tracił(by) precyzję w przeglądarce) — ustawiany wyłącznie przez samego zainteresowanego (`PATCH /api/roster/me/steam-id`, ten sam wzorzec co `InGameNickname`), waliduje dokładnie 17 cyfr ≥ najniższego wydanego SteamID64. Czytają go dwa miejsca, oba przy parsowaniu demki: dopasowanie graczy przy imporcie staty (`Features/Stats/ImportStatsFromDemo`) i rozpoznanie, po której stronie w danej rundzie stała nasza drużyna, przy wyliczaniu wyniku meczu (`Features/Results/Shared/DemoScoreCalculator`)
  - `Event` (Match / Tournament / Training / PickupGame / Scrim) → `Availability` (per user, per event, unikalny indeks na parze). Opcjonalne `Event.Opponent` (wolny tekst, max 100) — formularz pokazuje je tylko dla Match/Tournament/Scrim.
  - **Przeciwnik nie jest osobną encją.** Nazwa żyje jako wolny tekst w trzech miejscach (`OpponentNote.OpponentName`, `MatchResult.Opponent`, `Event.Opponent`), a profil (`Features/OpponentNotes/{GetOpponents,GetOpponentProfile}`) skleja je po kluczu `OpponentNames.ToKey` (trim + lower-case, w EF `x.Trim().ToLower() == key`). Wielkość liter i spacje nie rozbijają przeciwnika na dwóch; literówki już tak — dlatego każde pole nazwy w UI (`OpponentNameInput`) podpowiada znane nazwy przez `<datalist>`. Nazwa wyświetlana = ostatnio użyta pisownia.
  - `PlayerAvailabilityDay` — dostępność dzienna niezależna od wydarzeń (Available / PartiallyAvailable z zakresem godzin / Off), unikalny indeks `(UserId, Date)`. Edycja dnia z przeszłości zablokowana w handlerze (`SetDayAvailabilityHandler`, wyjątek dla Coach/Manager); frontend rozdziela widok na zakładki „Nadchodzące" (dziś + przyszłość, edytowalne) i „Historia" (tylko odczyt, osobna nawigacja tygodniami). Zmiana statusu i notatki zapisuje się od razu po kliknięciu (bez osobnego „Zapisz" poza notatką) — patrz `DayAvailabilityEditor`
  - `Vacation` — zakres dni wolnych gracza; w widoku tygodniowym nadpisuje dostępność dzienną na `Off` z flagą `IsVacation`. Pełne CRUD (`Features/Availability/{SetVacation,UpdateVacation,DeleteVacation}`) — edycja w miejscu zamiast usuń-i-dodaj-od-nowa, ta sama reguła autoryzacji co przy usuwaniu (właściciel lub Coach/Manager)
  - Logikę "efektywnego statusu dnia" (urlop > deklaracja > `NotSet`) trzyma jedna klasa `Features/Availability/Shared/EffectiveAvailabilityCalculator` — używa jej zarówno widok tygodniowy, jak i dashboard (dziś/jutro), żeby nie rozjechały się interpretacje urlopu
  - `TaskItem` → przypisany do `User`, status Todo/PendingReview/Done/NeedsRework (pełen cykl: zawodnik zgłasza `Todo`/`NeedsRework` → `PendingReview` przez `Features/Tasks/SubmitTaskForReview`, Coach/Manager zatwierdza do `Done` (`ApproveTask`) albo cofa do `NeedsRework` (`RejectTask`); `Features/Tasks/GetAllTasks` daje Coach/Managerowi podgląd zadań wszystkich zawodników z `DeleteTask` do kasowania pomyłek). Opcjonalny `DueAtUtc` i opcjonalny `TrainingMaterialId` (luźny link bez FK, jak `TacticPoint.NadeEntryId`) pozwalają Coach/Managerowi doczepić do zadania konkretny materiał z biblioteki do obejrzenia — `GetMyTasksHandler`/`GetAllTasksHandler` dołączają tytuł/URL materiału jednym `GroupJoin`, więc zawodnik widzi link bezpośrednio na liście swoich zadań, bez osobnego zapytania
  - `MatchResult` — wynik + opcjonalny link do demki (`DemoUrl`, zwykły string, nie plik). `OurScore`/`OpponentScore`/`MapName` na encji zostają nienullowalne, ale w `AddResultCommand` są opcjonalne: przy dodawaniu wyniku można dołączyć plik `.dem`, z którego handler wylicza wynik i mapę (patrz „Wynik i mapa z demki" niżej), a wpisane ręcznie wartości są wtedy tylko fallbackiem. `Category` (`MatchCategory`: Scrimmage/League/Tournament, string w bazie) rozróżnia typ rozgrywki; `TournamentId`/`LeagueId` to luźne linki (bez FK, jak `TacticPoint.NadeEntryId`) do `Tournament`/`League`, ustawione tylko gdy `Category` na to wskazuje (pilnuje `AddResultCommandValidator`, oba pola po obu stronach warunkowo — z jawnym `ApplyConditionTo.CurrentValidator`, bo domyślnie `.When()` w FluentValidation działa wstecz na cały łańcuch reguł danego `RuleFor`, nie tylko na poprzedzający walidator)
  - `Tournament` — `Id`/`Name`/`CreatedByUserId`/`CreatedAtUtc`, realna encja zamiast wolnego tekstu w `MatchResult`, żeby literówka w nazwie nie rozbijała grupowania wyników na `/results`
  - `League` — `Id`/`Name`/`Season` (wolny tekst, np. "2026 Wiosna")/`Type` (`LeagueType`: Online/Lan/Division1/Division2/Other, string w bazie)/`CreatedByUserId`/`CreatedAtUtc`
  - `NadeEntry` — per mapa (`MapName` jako enum: Dust2 / Mirage / Inferno / Nuke / Ancient / Anubis / Cache — aktualna pula 2026, w bazie trzymany jako string przez `HasConversion<string>`), typ granatu, link YouTube. Rotacja puli map = nowa wartość enuma + migracja normalizująca stare wpisy (wzór: `ConvertNadeMapNameToEnum`). Opcjonalna pozycja lądowania na radarze (`LandingX`/`LandingY`, ułamki [0,1] jak w `MapPositionAssignment`, nullable — stare wpisy bez pinezki nadal działają, pokazują się tylko na liście) ustawiana osobnym slice'em `Features/Nades/UpdateNadePosition` (autor wpisu lub Coach/Manager, jak przy usuwaniu), żeby nie psuć kontraktu `AddNade`
  - `MapPositionAssignment` — pozycja startowa jednego gracza na danej mapie i stronie (`MapSide`: CT / T, w bazie jako string). `X`/`Y` to **ułamki [0,1] względem radaru**, nie piksele — dzięki temu pinezki są niezależne od rozmiaru obrazu i skalują się z kontenerem. Unikalny indeks `(MapName, Side, UserId)` = jeden gracz ma jedno miejsce na mapie/stronie, a slice `Features/MapStrategy/SetPlayerPosition` robi po tym kluczu upsert (wzór jak `SetAvailability`)
  - `MapTextAnnotation` — dowolna notatka tekstowa na radarze (np. opis miejscówki), **nieprzypisana do gracza** — w przeciwieństwie do `MapPositionAssignment` może ich być wiele na tej samej mapie/stronie, więc brak unikalnego indeksu, tożsamość to zwykłe `Id`. `X`/`Y` — te same ułamki [0,1] co w `MapPositionAssignment`. `Color` (hex string) i `FontSizePx` (10-40) są edytowalne z poziomu frontu razem z treścią, przez jeden slice `Features/MapStrategy/UpdateTextAnnotation` (przeciąganie pinezki i edycja stylu/treści to ta sama komenda, tylko inne pola się zmieniają). CRUD: `AddTextAnnotation`/`UpdateTextAnnotation`/`RemoveTextAnnotation`/`GetMapTextAnnotations`, wszystkie poza odczytem ograniczone do Coach/Manager. Radar na froncie (`MapRadar.tsx`) obsługuje też scroll-zoom + pan (`useMapZoom` — transform `scale`/`translate` na wewnętrznym kontenerze, licznik pozycji pinezek liczony z jego `getBoundingClientRect()`, więc działa niezależnie od aktualnego przybliżenia)
  - `Tactic` → `TacticPoint` (1-do-wielu, kaskadowe usuwanie) — zapisana taktyka drużyny per mapa i strona (`MapSide`), z tagiem ekonomii (`EconomyType`: Eco/ForceBuy/FullBuy/AntiEco) i dowolną liczbą ponumerowanych punktów na radarze (`X`/`Y` — te same ułamki [0,1] co w `MapPositionAssignment`), z których każdy ma opcjonalny opis i opcjonalny luźny link do `NadeEntry.Id` (bez FK, jak `CreatedByUserId` gdzie indziej). W przeciwieństwie do `MapPositionAssignment` (jedna pozycja na gracza) punkty taktyki nie są przypisane do konkretnego gracza — to plan, nie obsada. Tworzy/edytuje/usuwa wyłącznie Coach/Manager (`Features/Tactics/UpdateTactic` zapisuje metadane **i** cały układ punktów jedną komendą — edytor wysyła kompletną listę na każdy "Zapisz", stare wiersze kasowane jawnie przez `DbSet.RemoveRange` zamiast liczyć na wykrywanie zmian w kolekcji nawigacyjnej, bo EF Core oznacza nowo dodane encje z jawnie ustawionym kluczem jako `Modified`, nie `Added`, gdy trafiają do śledzonego kontekstu przez samą nawigację). Odczyt (lista + szczegóły) dla całej drużyny.
  - `TrainingMaterial` — link + kategoria (`MaterialCategory`: Grenades/Tactics/Aim/Positioning/VodReview/Communication/Other, string w bazie przez `HasConversion<string>`, opcjonalna — lista rozwijana na froncie zamiast dawnego wolnego tekstu)
  - `MapPoolEntry` — status mapy w puli drużyny (`MapPoolStatus`: Core/Playable/Learning/Ban, string w bazie) + krótka uwaga; unikalny indeks na `MapName`, brak wiersza = mapa nieustalona. `Features/MapPool/GetMapPool` zawsze zwraca **wszystkie** mapy z enuma `MapName`, a bilans liczy z `MatchResult.MapName` (wolny tekst, dopasowywany do enuma `Enum.TryParse(ignoreCase)` po `Trim`; mapy spoza puli, np. Overpass, są pomijane). Opcjonalny filtr `MatchCategory`.
  - `EventVetoStep` — jeden krok veto przy wydarzeniu (`Order` 1..n, `VetoActor` Us/Opponent, `VetoAction` Ban/Pick/Decider, `MapName`); unikalne indeksy `(EventId, Order)` i `(EventId, MapName)`, bez FK — jak `Availability`, kroki usuwa `DeleteEventHandler`. Zapis to podmiana całej listy jednym `SaveChanges` (EF sortuje DELETE przed INSERT przy konflikcie unikalnego indeksu — sprawdzone na Postgresie). **Sugestia veto** (`Features/Veto/GetVetoSuggestion`) to świadomie prosta, addytywna punktacja w czystej klasie `VetoScoring` (status w puli, wygrane z wygładzeniem Laplace'a, bilans z przeciwnikiem, jego picki/bany z zapisanych veto, liczba taktyk) — każdy składnik ma zdanie w `Reasons`, żeby trener wiedział, co i dlaczego nadpisuje. Banujemy 3 mapy (bany z puli liczą się pierwsze), pickujemy 2 z dodatnim wynikiem, zawsze zostają co najmniej 2 mapy niezbanowane.
  - `EventGamePlan` (notatka planu, max 4000, unikalny indeks na `EventId`) + `EventGamePlanItem` (`GamePlanItemKind` Tactic/AnalysisBoard, `TargetId`, `Order`; unikalny indeks `(EventId, Kind, TargetId)`). `TargetId` to miękka referencja bez FK: usunięta taktyka/tablica po prostu znika z planu przy odczycie (`GamePlanReader`), zapis odrzuca nieistniejące ID (`GamePlan.UnknownItems`). Zapis podmienia cały plan; kroki i plan kasuje `DeleteEventHandler`. Linki głębokie: `/playbook?tab=tactics&tactic=…`, `/playbook?tab=boards&board=…`, `/calendar?event=…` (rozwija wydarzenie) — wybrany element wyliczany z URL, bez `useEffect`.
- **Autoryzacja**: logowanie wyłącznie przez **Discord OAuth2** (`/api/auth/discord/login` → redirect do Discorda → `/api/auth/discord/callback` wymienia kod na profil przez `IDiscordOAuthClient`, znajduje-lub-tworzy `User` po `DiscordId`, wystawia JWT i przekierowuje do frontendu z tokenem we fragmencie URL `#token=`). Świadoma decyzja: zero haseł, zero przechowywanych danych logowania — tożsamość i zgoda żyją tylko po stronie Discorda. Scope `identify guilds` + `DiscordOAuth:RequiredGuildId` — jeśli ustawiony, logowanie sprawdza (`GET /users/@me/guilds`) czy dana osoba faktycznie jest na serwerze Discord drużyny i odrzuca każdego innego; bez tego dowolne konto Discord mogłoby wejść do środka. **Każde nowe konto startuje jako `Guest`** — jest zalogowane, ale nie widzi żadnych danych drużyny, dopóki Manager nie nada mu roli przez ekran Skład (`PATCH /api/roster/{userId}/role`). Ponieważ nikt nie może zmienić własnej roli, pierwszy Manager musi zostać ustawiony ręcznie w bazie (patrz [DEPLOYMENT.md](DEPLOYMENT.md)). **Usuwanie nieaktywnego zawodnika** (`DELETE /api/roster/{userId}`, Manager only, `Features/Roster/DeleteTeamMember`) kasuje konto i tylko jego prywatne dane (dostępność, urlopy, pozycja na radarze, dodatkowe role w grze, zadania *przypisane jemu*) — nie może usunąć samego siebie (`RosterErrors.CannotDeleteOwnAccount`, ta sama ochrona co przy `CannotChangeOwnRole`). Wspólny dorobek drużyny (wyniki meczów, granaty, taktyki, materiały, zadania które *on* przydzielił innym) zostaje nietknięty — żadna z tych encji nie ma w bazie realnego klucza obcego do `User`, więc usunięcie konta zostawia tam po prostu martwy Guid zamiast wywoływać kaskadę. Jedyne miejsce, które faktycznie rozwiązuje taki Guid na wyświetlaną nazwę — `GetMatchStatsHandler` (panel staty meczu) — dostało `LEFT JOIN` z fallbackiem `"Usunięty zawodnik"` zamiast dawnego `INNER JOIN`, który po cichu wycinałby wiersz usuniętego gracza. Sesja usuniętego konta obumiera przy najbliższym `POST /api/auth/refresh` (wołanym automatycznie przy starcie apki i powrocie fokusu okna) — `RefreshSessionHandler` zwraca wtedy `AuthErrors.UserNotFound`, a `apiClient` czyści sesję i przerzuca na `/login`, bez potrzeby osobnego blacklistowania JWT.
  - Egzekwowanie: polityka `AuthorizationPolicies.TeamMember` (`RequireRole("Player", "Coach", "Manager")`, rejestrowana w `Program.cs`) wisi na **każdej** grupie `MapGroup(...)` z danymi drużyny oraz na `TeamHub` — Gość dostaje 403, nie 401 (pozostaje działać bez zmian: Trener zawsze niesie też `AccessLevel` Player/Manager, więc claim "Player"/"Manager" i tak jest obecny). Dodatkowe `RequireRole("Coach", "Manager")` / `RequireRole("Manager")` na pojedynczych endpointach zostają bez zmian (są podzbiorem `TeamMember`); tam gdzie trzeba sprawdzić "właściciel zasobu LUB Coach/Manager" (np. usuwanie granatu), logika jedzie w handlerze przez `ICurrentUserService.Role == "Manager" || ICurrentUserService.IsCoach`.
  - Frontend lustrzanie: `ProtectedRoute` dla roli `Guest` renderuje `PendingAccessPage` zamiast żądanej strony, a `Layout` chowa całą nawigację (zostaje avatar, komunikat "konto oczekuje na przydzielenie roli" i Wyloguj).
  - **Długość sesji**: JWT ważny `Jwt:ExpiryMinutes` = **43200 minut (30 dni)**. Świadomie bez refresh tokenów — to wewnętrzne narzędzie jednej drużyny, a długi token wymienia dodatkową infrastrukturę na brak logowania co godzinę. Po faktycznym wygaśnięciu `apiClient` łapie 401, czyści sesję (`useAuthStore.clearSession()`) i przerzuca na `/login`. `Program.cs` odmawia startu, gdy `Jwt:Secret` jest puste — inaczej każdy restart backendu cicho podpisywałby tokeny pustym kluczem i unieważniał wszystkie sesje naraz.
  - **Zmiana roli bez ponownego logowania**: rola (`ClaimTypes.Role`) jest zaszyta w JWT tylko przy jego wystawieniu, więc awans Gościa przez Managera sam z siebie nie dotrze do już otwartej karty. `POST /api/auth/refresh` (dowolny zalogowany, Gość włącznie — jedyny endpoint poza `/api/auth/discord/*` bez wymogu `TeamMember`) odczytuje aktualną rolę z bazy i wystawia nowy token; frontend (`SessionRefresh` w `App.tsx`) woła go przy starcie apki i przy każdym powrocie fokusu okna.
- **Storage plików**: demka CS2 bywają duże (100–300 MB) — świadomie NIE wdrożono własnego uploadu do S3-compatible storage w tej fazie (brak realnych danych dostępowych do bucketa do przetestowania). `MatchResult.DemoUrl` to zwykły link do zewnętrznie hostowanego pliku (Drive, itp.); prawdziwy upload z presigned URL to follow-up, gdy pojawi się konto np. na Cloudflare R2.
- **Import staty z demki** (`POST /api/stats/import-demo`, Coach/Manager) oraz **wynik z demki** (`POST /api/results`, ten sam zakres ról): jedyne dwa miejsca, gdzie apka w ogóle dotyka bajtów pliku — `IFormFile.OpenReadStream()` idzie prosto do parsera, nic nie trafia na dysk ani do S3. `IDemoParser` (interfejs w `Application/Abstractions`) implementuje `DemoFileParser` (`Infrastructure/Demos/`) na bibliotece `DemoFile`/`DemoFile.Game.Cs` (github.com/saul/demofile-net) — ta sama inwersja co `IDiscordNotifier`/`IRealtimeNotifier`, dzięki czemu `ImportStatsFromDemoHandler` ma testy jednostkowe na fake'owym parserze, bez prawdziwego pliku `.dem`. Oba endpointy podnoszą limit rozmiaru requestu (Kestrel domyślnie 30 MB) do 320 MB przez `IHttpMaxRequestBodySizeFeature`, tylko dla siebie — i **osobno** `FormOptions.MultipartBodyLengthLimit` (własny, niezależny limit 128 MB w `ReadFormAsync`, który bez tego cicho odrzuca większe demka).
- **Wynik i mapa z demki**: `POST /api/results` przyjmuje `multipart/form-data` z opcjonalnym polem `demo`. `DemoFileParser` obok staty zbiera też `DemoRoundResult` na rundę (zwycięska strona + SteamID-y po obu stronach, budowane ze zdarzeń `PlayerTeam`/`RoundEnd`), a `DemoScoreCalculator` (`Application/Features/Results/Shared`, czysta funkcja, własne testy) dla **każdej rundy z osobna** sprawdza, po której stronie stała większość naszego składu — dzięki temu zmiana stron na połowie i w dogrywce nie wymaga żadnej dodatkowej logiki. Dopasowanie żyje w Application, nie w parserze, bo wymaga dostępu do składu (`IApplicationDbContext`), a `Infrastructure`/`Core` nie mają prawa wiedzieć o rosterze. Gdy żadnej rundy nie da się przypisać (nikt ze składu nie ma jeszcze `SteamId64`), kalkulator zwraca `null` i liczy się ręcznie wpisany wynik; brak jednego i drugiego to `ResultErrors.ScoreRequired`.

Wynik to `DemoTimeline` (`Application/Abstractions`): `Stats` (dawny `DemoParseResult`), `Rounds` (`DemoTimelineRound`) i `Grenades` (`DemoGrenade`) — płaskie listy kluczowane numerem rundy, pozycje jako `DemoPosition` (świat + ułamek radaru, `null` bez kalibracji; przeliczane w builderze, gdy mapa jest już znana). Nowy rodzaj danych = nowa flaga + nowy kolektor + nowa lista w `DemoTimeline`. `ParseAsync(stream, ct)` zostało jako skrót „tylko statystyki" dla importu staty/wyniku.

Odczyt: `GET /api/results/{id}/timeline` i `/insights` (`MatchTimelineLoader` → `MatchTimelineMapper` → `MatchInsightRules`, wszystko czyste i testowane), dołączenie demki do istniejącego meczu: `POST /api/results/{id}/demo` (klucz z presigned uploadu, regex `demos/{guid}`). „My" = SteamID-y z wyboru drużyny w formularzu, w przeciwnym razie `TimelineTeamResolver` (skład, potem zgodność z zapisanym wynikiem); strona per runda większością, jak `DemoScoreCalculator`. - **Zadania w tle** (`Application/Common/Jobs`, `Features/Jobs`, `Infrastructure/Jobs`): długie operacje (analiza demki do wyniku — bezpośredni upload `AnalyzeUploadedDemo` i presigned `AnalyzeDemoFromStorage`, `AttachDemoToResult`, `AnalyzeOpponentDemo`, `ExtractDemoNades`, `DownloadOpponentDemos`, `LinkAndSyncOpponentFaceit` = powiązanie + pierwsza synchronizacja, ręczne `SyncOpponentFaceit`) nie wykonują się w requeście. Odpowiedź: `202 { jobId }` + `Location: /api/jobs/{id}`. `BackgroundJobWorker` (hosted) trzyma `Jobs:DemoConcurrency` (2 — parsowanie demek jest pamięciożerne) i `Jobs:FaceitConcurrency` (2) konsumentów; każde zadanie to trzy scope'y DI: oznaczenie Running (`JobStateStore.TryStartAsync`), wykonanie (`JobExecutionContext.Begin` → zwykły `ISender.Send` requestu, czyli handler MediatR jak każdy inny; `JobRunner` zamienia wynik/błąd biznesowy/timeout/zatrzymanie/wyjątek na `JobOutcome` z polskim komunikatem) i zapis wyniku (`ResultJson` w kształcie dawnej odpowiedzi — `JobJson` = web defaults + enumy jako stringi), więc DbContext handlera nigdy nie miesza się z zapisem statusu. Postęp: `IJobProgress` (scoped, poza zadaniem no-op) z `Report(%)`, `BeginStep(od, do, etap)`, `ReportStep(ułamek)`; `ProgressReportingDemoParser` dekoruje `DemoFileParser` i raportuje odczytane bajty strumienia (`ProgressReportingStream` — liczy bajty, nie pozycję, więc seek nie skacze do 100%), domyślnie w oknie 5–95% „Analiza demki”, potem „Zapisywanie wyników”; pobieranie z FACEIT dzieli pasek na demki, synchronizacja FACEIT raportuje etapy. `JobProgressSink` dławi zapisy (`ProgressThrottle`: zmiana etapu albo wyższy % co ≥ 750 ms), pisze `ExecuteUpdate` tylko do wiersza w stanie Running i pushuje `job:{id}` oraz `jobs:{userId}` przez `IRealtimeNotifier` (temat bez danych — klient pobiera `GET /api/jobs/{id}`, który wpuszcza zlecającego albo Coach/Manager). `ICurrentUserService` w zadaniu zwraca zlecającego (`JobExecutionContext`), bo nie ma `HttpContext`. **Kolejka nie przeżywa restartu**: przy starcie worker oznacza zadania Queued/Running utworzone przed startem procesu jako Failed („przerwane przez restart serwera — uruchom ponownie”) i usuwa zakończone starsze niż `Jobs:RetentionDays` (7); przerwana demka zostaje w S3 do reguły cyklu życia bucketa. Frontend: `features/jobs` — `useJob(jobId)` (TanStack Query, `job:{id}` z `realtime.ts` unieważnia `['jobs', id]`, polling co 2 s bez połączenia live / co 10 s z nim), `useBackgroundJob(start, { onSucceeded, slot })` (upload + start + śledzenie; `slot` trzyma id w `useJobStore`, więc postęp np. pobierania demek rywala wraca po ponownym wejściu na stronę) i `JobProgress` (pasek + etap + błąd).

## Frontend — React + TypeScript

- **Vite** + **TailwindCSS**, komponenty w stylu shadcn/ui.
- **React Query** do stanu serwera (cache, refetch, dedupe requestów), **Zustand** do stanu UI/lokalnego.
- **vite-plugin-pwa** — instalacja na telefonie (prawdziwe ikony w `public/`, wygenerowane bez zewnętrznych narzędzi), cache dla widoków statycznych działający offline. Manifest i service worker działają tylko w buildzie produkcyjnym (`vite build`/`preview`), nie w `vite dev` — tak działa plugin domyślnie.
- **`@microsoft/signalr`** — `RealtimeSync` (w `App.tsx`) trzyma jedno połączenie do `/hubs/team` dopóki użytkownik jest zalogowany; odbiera topic i wywołuje `queryClient.invalidateQueries`.

- Kalendarz dostępności jako siatka tydzień × zawodnik z kolorami (dostępny / częściowo dostępny z zakresem godzin / off / urlop) — `features/availability/` na stronie `/calendar` (zakładka „Dostępność”; zakładka „Wydarzenia” to lista wydarzeń, urlopy za przyciskiem „Urlopy”): nawigacja po tygodniach, edycja wyłącznie własnego wiersza (mocno podświetlonego — tło + `ring` + pogrubiony nick, nie tylko subtelne tło), pod każdą kolumną dnia licznik „X/Y dostępnych" + wspólne okno godzinowe (`computeDaySummary` — czysto frontowe wyliczenie z danych już zwróconych przez `GET /week`, bez osobnego zapytania) i lista nieobecnych, nad kolumną znacznik wydarzenia z `useUpcomingEvents()`. Zakładki „Nadchodzące"/„Historia" (druga tylko do odczytu). Wiersze sortowane w sekcjach z kreską (`border-t`) między nimi: main skład → ławka → Trener zawsze na końcu we własnej sekcji z nagłówkiem „Trener" (`sectionOf`/`sectionRank` w `WeeklyCalendar`, niezależnie od jego `RosterSlot`); backend (`GetWeekAvailabilityHandler`) już wcześniej wyklucza z zapytania każdego bez slotu w składzie i bez `IsCoach`, więc "Pozostali" nigdy nie trafiają do kalendarza. Klik w dzień otwiera `DayAvailabilityEditor`: checkbox „Cały dzień" zaznaczony domyślnie (jeden przycisk „Dostępny"), odznaczenie pokazuje zakres godzin zamiast osobnego statusu „częściowo dostępny" — pod spodem to nadal ten sam `PartiallyAvailable`. Urlopy (`VacationForm`/`VacationList`, edycja w miejscu) nadpisują status dnia po stronie backendu. Live-update przez topic `availability-week` → invalidacja klucza `['availability','week']`.
- Nawigacja: boczny pasek (`app/nav/`: `Sidebar`, `SidebarNav`, `navItems.ts`; desktop od `lg` stały 240 px, zwijany do paska ikon 64 px — stan w `localStorage` pod `harnashub.sidebarCollapsed`; na telefonie górny pasek z hamburgerem otwierający ten sam pasek jako szufladę) z sekcjami zawsze rozwiniętymi: Dashboard · Kalendarz (`/calendar`, zakładki Wydarzenia/Dostępność) · Mecze (Wyniki → `/results/:id`, Przeciwnicy, Rozwój) · Playbook (`/playbook?map=…&tab=positions|nades|tactics|boards|materials|pool|stats`) · Drużyna (Skład, Zadania, Frekwencja). Stare ścieżki (`/events`, `/nades`, `/map-strategy`, `/tactics`, `/analysis-boards`, `/materials`, `/maps`) przekierowują (`LegacyRedirect` w `AppRouter`) z zachowaniem query stringa. Formularze „Dodaj…” otwierane są przyciskiem w modalu (`components/AddFormModal`). Strona meczu `/results/:id` (`MatchDetailPage`) ma zakładki Przegląd / Rundy / Gracze (`features/match-analysis/`: `MatchTabs`, `MatchInsightsPanel`, `RoundTimeline`/`RoundRow`, `AttachDemoButton` — presigned upload + `POST /api/results/{id}/demo`); brak osi czasu (404) to stan oczekiwany, nie błąd.
- Kolory: semantyczne tokeny Tailwind v4 (`@theme` w `frontend/src/index.css`) — `primary-*` (złoto/bursztyn: akcje, aktywne zakładki i nawigacja, fokus), `danger-*` (usuwanie, błędy, przegrane, negatywne wnioski), `success-*` (wygrane, pozytywne), `warning-*`, `info-*`, `side-t`/`side-ct` (strony CS), `brand` (czerwone „Hub” w logo — jedyny czerwony akcent marki) oraz powierzchnie `surface-*`. Wspólne prymitywy w `components/ui/` (`Button`, `Tabs`, `PageHeader`). Czerwień nie oznacza już akcji głównej.
- Pozycje startowe (`features/map-strategy/` w zakładce „Pozycje” strony `/playbook`) — radar wybranej mapy (`public/maps/<mapa>.webp`, nazwa pliku = lowercase wartość enuma `MapName`) w kontenerze `position: relative`, na nim pinezki graczy pozycjonowane procentowo z `X`/`Y`, kolor z `User.PinColor` gdy ustawiony (inaczej hash z `UserId`). Coach/Manager przeciąga pinezkę, żeby zmienić pozycję (pointer events z `setPointerCapture`, zapis **raz**, na `pointerup` — nie na każdym `pointermove`), a zwykłe kliknięcie (bez ruchu) otwiera edytor notatki „co robić na tej pozycji" (`PositionNoteEditor`, autosave); notatki wszystkich pozycji zebrane też w czytelnej liście pod radarem. Zwykły gracz widzi tooltip z nickiem i rolą w grze plus tę samą listę notatek. Live-update przez topic `map-strategy`.
- Wyniki (`features/results/` na stronie `/results`) — `AddResultForm` ma select kategorii (Sparing/Liga/Turniej) i warunkowy picker turnieju/ligi z inline tworzeniem nowego wpisu bez opuszczania formularza (`TournamentPicker`/`LeaguePicker`). `ResultList` grupuje wyniki: sparingi płasko, turnieje/ligi w sekcjach nazwanych turniejem lub sezonem+typem ligi (`groupResults`, czysto frontowe, z już zwróconych przez `GET /results` danych). Rozwinięty wiersz wyniku (`MatchStatsPanel`, `features/stats/`) ma dla Coach/Managera, obok ręcznego formularza, `DemoImportPanel` — wgrywa plik `.dem`, pokazuje edytowalną tabelę podglądu (dopasowanie po `SteamId64`, reszta jako "Niedopasowany" z ręcznym wyborem z listy), zapis per-wiersz reużywa istniejący `AddPlayerStat`.
- Granaty (`features/nades/` w zakładce „Granaty” strony `/playbook`) — przełącznik Lista/Mapa (`NadesTab`). Lista (`NadeLibrary`) filtruje po mapie/typie, osadza wideo inline. Mapa (`NadeMapView`) — wybór mapy, radar z pinezkami (`NadePin`) kolorowanymi i oznaczonymi literą po `GrenadeType`, filtr typu checkboxami; klik w pinezkę pokazuje kartę ze szczegółami i wideo, przeciągnięcie zmienia pozycję (wzorzec `pointer-capture` jak `MapRadar`/`TacticEditor`) — dostępne tylko autorowi wpisu lub Coach/Managerowi. Wpisy bez pinezki trafiają do listy "Bez pozycji na mapie" z przyciskiem uzbrajającym tryb umieszczenia; kolejny klik na radarze zapisuje pozycję (`PATCH /api/nades/{id}/position`). Live-update przez topic `nades`. Wideo osadzane przez współdzielony `components/YoutubeEmbed.tsx`: parsuje link (watch/youtu.be/embed/shorts, z opcjonalnym `t=`/`start=`), embeduje przez `youtube-nocookie.com` (privacy-enhanced), renderuje miniaturkę z przyciskiem play zamiast żywego `<iframe>` dopóki ktoś nie kliknie ("facade" — bo lista granatów na mapie potrafi mieć kilkadziesiąt klipów naraz).
- Biblioteka taktyk (`features/tactics/` w zakładce „Taktyki” strony `/playbook`, złożonej w `TacticsTab`) — karty filtrowane po mapie/stronie/ekonomii (`TacticList`), klik otwiera `TacticEditor`: radar z ponumerowanymi, przeciąganymi pinezkami (`TacticPin`, wzorem `map-strategy`, ale bez powiązania z konkretnym graczem) i panelem notatek pod spodem. Zmiany pinezek żyją tylko w lokalnym stanie komponentu, dopóki Coach/Manager nie kliknie „Zapisz" — jeden `updateTactic` wysyła metadane i cały układ naraz, więc kliknięcie pustego miejsca na radarze (dodanie punktu), przeciąganie i usuwanie punktów nie generują osobnych zapytań. Klik na pinezkę otwiera `TacticPointEditor` z opisem punktu i selectem podpinającym konkretny wpis z `useNades` (tej samej mapy) jako link do lineupu. Zwykły gracz widzi tę samą listę/filtr/edytor w trybie tylko-do-odczytu (bez formularza tworzenia, bez przycisków „Zapisz"/„Usuń", pinezki nieprzeciągalne). Live-update przez topic `tactics`.
- Skład (`features/roster/` na stronie `/roster`) — lista z jednym popoverem na całość ról w grze (`TeamRolesEditor`, dawniej dwa osobne selecty: checkbox włącza rolę, gwiazdka oznacza, która jest główna — jedna mutacja `updateTeamRole` + jedna `updateSecondaryTeamRoles`), statusem w składzie i osobno: checkboxem „Trener" (`IsCoach`, niezależny od uprawnień) i selectem uprawnień (`AccessLevel`: Gość/Zawodnik/Zarządca, oba z tooltipem opisującym co dają). Kolor pinezki **nie** siedzi już w wierszu — Manager przypisuje go w osobnym `PinColorAssignmentPanel` nad tabelą (tylko dla 5 graczy Main), żeby nie ściskać nicku w wierszu do zera szerokości. Dla Coach/Manager dodatkowo `RosterBoard` — trzy kolumny (Main/Bench/Pozostali) z przeciąganiem kart (`@dnd-kit/core`), Main wygasza się i przestaje podświetlać drop po osiągnięciu 5 graczy; upuszczenie karty w kolumnie woła ten sam `PATCH .../roster-slot` co dropdown w liście.
- Ustawienia (`/settings`, koło zębate obok nicku w pasku) — własny nick (ustaw/zmień/wyczyść) i, dla zawodnika głównego składu, wybór koloru pinezki.
- Dashboard (`features/dashboard/`) nad trzema kafelkami (najbliższe wydarzenie / otwarte zadania / skuteczność) pokazuje sekcje „Dzisiaj" i „Jutro" — `DailyStatusCard` renderuje wydarzenie danego dnia i listę graczy podzieloną na grających i nieobecnych, reużywając `DayStatusBadge` z `features/availability`. Dane idą jednym zapytaniem `GET /api/dashboard` (pola `today`/`tomorrow`).
- Odtwarzacz 2D (`features/match-analysis/components/RoundReplay*`, `replay/`): `buildSeries` rozpakowuje klatki raz do `Float32Array` per gracz, `useReplayPlayback` trzyma czas ułamkowy w `ref` i co klatkę `requestAnimationFrame` woła subskrybentów, a stan Reacta zmienia tylko przy pełnej sekundzie (suwak, kill feed). `ReplayCanvas` rysuje imperatywnie (`drawReplay`) na canvasie nad obrazem radaru, skalowanym do `devicePixelRatio` przez `ResizeObserver`. Wejścia: zakładka Rundy meczu (rozwiń rundę → „Odtwórz”, modal z poprzednią/następną rundą) i lista demek rywala (wybór rundy → „Odtwórz”). Dopasowane taktyki i skuteczność: `useMatchTacticMatches`/`useTacticEffectiveness` (klucze pod `['tactics', …]`, więc każda edycja taktyki je odświeża).

## Hosting

Jeden deploy, jeden URL — backend serwuje zbudowany frontend. Pełen plan, konfiguracja i checklista testowa: [DEPLOYMENT.md](DEPLOYMENT.md).

## Rozważane później (nie w MVP)

- Filtr po `MatchCategory`/turnieju/lidze na `/stats` i wykresie trendu drużynowego (`GetTeamTrendQuery`) — dziś liczy wszystkie wyniki razem, więc sparing z kumplami i faza grupowa turnieju trafiają do tej samej krzywej skuteczności.
- Wewnętrzny ranking/ELO na bazie wyników sparingów, liczony z już istniejących `MatchResult`/`PlayerMatchStat`.
- Prawdziwe powiadomienia push (VAPID + custom service worker) — po realnym wdrożeniu, gdy jest na czym testować zgodę przeglądarki.
- Upload plików (demek) do własnego storage (Cloudflare R2) zamiast linków zewnętrznych.
